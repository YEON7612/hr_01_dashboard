# 나의 분석 워크플로우 (트랙 B — HR 대시보드)

프레임워크: Define → Acquire → Profile → Confirm → Clean → Model → Analyze → Validate → Publish → Approve&Send

**작성 방식에 대한 안내**: 이 문서는 Day4까지 미리 계획한 것이 아니라, 이미 진행한 작업을 오늘(Day5) 이 프레임워크에 맞춰 역으로 재정리한 것입니다. 따라서 "계획 대비 실제 비교"는 온전히 할 수 없고, "실제로 겪은 일"만 정확히 기록합니다. 앞으로는 이 문서를 먼저 쓰고 실행하는 순서로 바꿉니다.

작성일: 2026-08-01

---

## 1. Define — 질문 정의

**오늘의 질문**: 직원들은 왜 퇴사하는가? (부서/직급/근속연수/초과근무/평가/채용경로 중 어떤 요인이 퇴사와 관련 있는가)

- 프레임워크: AARRR을 HR에 맞게 재매핑(채용/온보딩/재직유지/추천채용/성과)해서 사용
- **확정(2026-08-01)**: Referral 단계 중 "추천인당 성공 건수", "추천을 많이 한 직원이 더 오래 다니는가"는 답할 수 없음으로 최종 확정. 인사팀에 추천인-피추천인 연결 기록 자체가 없음을 확인함. 대리 지표로 채우지 않고 ❌로 유지 (근거: `설계서_data_hr_referrals.md`)

## 2. Acquire — 데이터 확보

**확보 경로 확정(2026-08-01)**: ① 원본 반출. 사번만 있고 이름·연락처 등 직접 식별 정보가 없으며, 반출 승인된 상태로 확인함. (Day3 기준: 인사 데이터는 전형적으로 ③ 구조복제후합성이 흔하지만, 이번 경우는 실제 반출이 승인되어 원본을 그대로 사용함)

**확보한 파일**: HR_직원.csv, HR_근태.csv, HR_퇴사이력.csv, HR_평가.csv (이후 HR_직원.csv에 채용경로 컬럼 추가되어 재업로드됨)

**실제 있었던 일**: 채용경로 컬럼이 추가된 재업로드본이 인코딩 손상 상태로 들어옴 (UTF-8/EUC-KR 혼용). 이 문제는 계획에 없던 것으로, Acquire 단계에서 예상하지 못한 리스크였음.

**확인 필요**: 앞으로 파일이 추가/수정되어 재업로드될 때, 인코딩 검증을 Acquire 직후 자동으로 하는 절차가 아직 없음 (수작업으로만 발견함)

## 3. Profile — 진단

- 행수/열수/컬럼명/데이터타입/결측치/고유값 확인 완료
- 이상값 발견: 특정 사번(E0137)의 근태 데이터가 12개월 내내 평균 대비 3배 이상 높음
- 커버리지 문제 발견: HR_평가·HR_근태는 2025년 한 해분만 존재 (HR_직원 입사일은 2015년까지 존재)

## 4. Confirm — 의미 확인

- "한 행 = 한 사번 × 한 기간(월/분기)"이라는 구조는 확인함
- **확인 필요**: 재직상태='퇴사'가 정확히 언제 시점 기준으로 반영되는지(데이터 스냅샷 시점)는 명시적으로 확인하지 않음
- 재직상태 ↔ 퇴사이력 교차검증은 완료 (양방향 불일치 없음 확인)

## 5. Clean — 정제

**실제로 있었던 문제**: HR_직원.csv 재업로드본의 부서/직급/재직상태 필드가 인코딩 손상으로 깨짐 (원인: UTF-8 저장 중 일부 바이트 유실 추정)

**정제 규칙**: `HR_데이터_정제규칙.md`에 9개 규칙으로 문서화 완료 (인코딩, 키값, 날짜형식, 범주형 화이트리스트, 결측치, 정합성, 이상값, 중복행, 재업로드 체크리스트)

**정제 스크립트**: `clean_hr_직원.py` — 아래 순서로 재실행 가능하게 만듦
1. 표준 UTF-8 로드 시도
2. 실패 시 바이트 단위 필드별 재디코딩(UTF-8→cp949)
3. 그래도 화이트리스트 위반이면 신뢰 스냅샷과 사번 기준 병합 복구
4. 최종 검증(화이트리스트 통과 여부) 후 저장

**검증 결과** (오늘 실행):
- 손상 재현 파일(300행) → 원본과 100% 일치 복구 확인
- 멱등성 확인: 정제된 파일에 재실행해도 동일 결과
- 행 수 무관 동작 확인: 50행 부분 데이터에서도 하드코딩 없이 작동

## 6. Model — 파생 지표 정의

- 근속연수 = (퇴사일 또는 기준일 - 입사일) / 365
- 평가점수 = 등급(S~D)을 5~1점으로 환산
- 채용경로 화이트리스트: 공채/수시/추천/헤드헌팅
- **추정연봉(⚠️ 공개 데이터 대체, Day3 확보경로 ④)**: 실제 급여 데이터 회신 대기 중 → 잡코리아 직급별 평균연봉 공개 통계로 임시 대체. 반드시 "실제 아님"을 명시하고, 실제 데이터 도착 시 폐기·재계산 예정

## 7. Analyze — 지표 계산

- 부서/직급별 퇴사율, 근속연수별 이탈 분포, 퇴사 직전 초과근무 신호
- 채용경로별 비중·퇴사율·근속연수 (추천채용 퇴사율 0% 발견, 표본 27명)
- 분기별 성과 추이 (전사 +0.18, 개발부서 +0.83)
- **인건비 효율(추정치)**: 개발 부서가 성과점수당 인건비 효율 최고(1,418만원)이면서 동시에 퇴사율도 최고(19.2%) — 낮은 처우와 이탈의 관계 가능성. 공개 통계 기반이라 확정적 결론 아님

## 8. Validate — 대조 검증

**✅ 완료.** 두 단계로 검증함:

1. **내부 재계산 대조**: 5개 항목(전체/퇴사 인원, 채용경로별 퇴사율, 부서별 퇴사율, 키 정합성, 재직상태↔퇴사이력 정합성)을 독립적으로 재구현해서 대조 — 전부 일치
2. **외부 원본 대조**: 인사팀 원본 채용 대장과 대조 확인 완료 — **일치함** (2026-08-01 확인)

→ 계산 로직 정확성과 원본 데이터 정확성 둘 다 확인됨. 이 단계에서 더 이상 남은 "확인 필요" 없음.

## 9. Publish — 반영

**✅ 완료.**
- `app.py`에 "채용경로별" 탭 추가, GitHub에 커밋 완료
- `data/HR_직원.csv`를 채용경로 포함 버전으로 교체, GitHub에 커밋 완료
- Streamlit Cloud 자동배포 완료

## 10. Approve & Send

**초안 완료.** 인사팀(관계자) 공유용 이메일 초안 2종을 작성함 (핵심요약형 / 간결확인요청형). 실제 발송은 사용자가 진행. 초안에 아래 두 가지를 검토 요청 항목으로 명시함:
- 채용경로·부서 데이터가 인사팀 원본 대장과 일치하는지 대조 요청
- 급여 데이터 제공 가능 여부 (인건비 효율 지표 계산을 위해)

## 남은 "확인 필요" 항목 요약

| 단계 | 확인 필요 항목 |
|---|---|
| Define | 질문이 확보 데이터로 완전히 답변 가능한 범위인지 사전 정의 안 됨 |
| Acquire | 재업로드 시 인코딩 자동 검증 절차 없음 |
| Confirm | 재직상태 스냅샷 기준 시점 불명확 |
| Model | 인건비 효율은 공개 통계 추정치 — 실제 급여 데이터 오면 반드시 재계산 |
| Approve&Send | 초안만 작성됨, 실제 발송·승인은 미완 (급여 데이터 제공 여부 회신 대기 중) |

Validate·Publish는 완전히 종료됨. 다음에 데이터가 갱신되면, 이 문서의 Define부터 다시 채운 뒤 실행하는 순서로 진행합니다.

## Day5 발표·회고 (한 문장씩)

**확보하면서 가장 까다로웠던 것**: 컬럼이 추가된 재업로드 파일이 UTF-8/EUC-KR 인코딩 혼용으로 손상되어 있었는데, 겉보기엔 로드가 되니까(단, 한글이 깨진 채로) 문제를 늦게 알아챌 뻔했던 것.

**정제 규칙 중 가장 애매했던 것**: 표본이 작은 그룹(추천채용 27명, 헤드헌팅 11명)의 결과를 어디까지 "신호"로 보고 어디부터 "우연"으로 볼지 — 정량적 임계값 없이 계속 "표본이 작다"고 정성적으로만 판단한 부분.
