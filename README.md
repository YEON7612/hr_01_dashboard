# HR 퇴사 원인 진단 대시보드 (hr_01_dashboard)

"직원들은 왜 퇴사하는가?" 라는 질문 하나를 붙잡고, 부서·근속연수·초과근무·평가등급·채용경로 등의 요인과 퇴사의 관계를 데이터로 진단하는 Streamlit 대시보드 프로젝트입니다. EDATA 7기 KDT_Aiffel 과정의 실습 프로젝트로, 10단계 분석 워크플로우(Define → Acquire → Profile → Confirm → Clean → Model → Analyze → Validate → Publish → Approve&Send)를 따라 진행했습니다.

## 프로젝트 링크

- **GitHub 저장소(전체 코드)**: https://github.com/YEON7612/hr_01_dashboard
- **배포된 대시보드 앱(실제 작동 화면)**: https://hr01dashboard-azhenhefzpsmrs8i3jbcxy.streamlit.app/

## 실행 방법

```bash
pip install -r requirements.txt
streamlit run app.py
```

`app.py`는 실행할 때마다 `data/` 폴더의 CSV를 직접 읽어 모든 지표를 재계산합니다(숫자 하드코딩 없음). 사이드바에서 부서 필터와 다크모드를 켤 수 있고, 탭으로 "대시보드", "채용경로별", "개선 제안 리포트", "연차별 잔류율 분석"을 오갑니다.

## 데이터 관련 중요 제약 (반드시 읽을 것)

- **2026년 1분기 근태 데이터는 합성 데이터입니다.** 개인 단위 상관계수가 0.279로 낮아 개인별 추이 분석에는 쓸 수 없고, 부서 단위 집계만 신뢰할 수 있습니다(`지표정의서.md` 6번 항목 참고).
- **평가점수는 2025년 4개 분기만 존재**합니다. 2025년 이전 이력이 없어 장기 추이 분석 시 이 한계를 항상 병기해야 합니다.
- **추천채용(27명)·헤드헌팅(11명) 채용경로는 표본이 작습니다.** "추천+헤드헌팅" 병합(n=38)으로 최소표본은 통과시켰으나, 이탈 0건 구간의 95% 신뢰구간 상한은 rule of three로 약 7.9%까지 열려 있어 통계적으로는 "신호" 수준으로만 해석해야 합니다.
- **목표 잔류율(90%)의 출처가 확인되지 않았습니다.** 실제 인사팀이 정한 목표치인지 임의 설정값인지 불명확해, 대시보드 게이지 옆에 "출처 미확인 가정값" 캡션을 표시해두었습니다(`app.py`의 `TARGET_RETENTION_RATE`).
- **추천인당 성공 건수 등 리퍼럴 세부지표는 영구 계산 불가로 확정**되었습니다 — 인사팀에 추천인-피추천인 연결 기록 자체가 없습니다(`07_참고자료/설계서_data_hr_referrals.md`).
- **인건비 효율 지표는 폐기되었습니다** — 공개 통계 기반 추정치였고 실제 급여 데이터가 아니었기 때문입니다. 실제 급여 데이터가 확보되면 재작성 대상입니다(`지표정의서.md` 9번 항목).
- **초과근무↔이탈 인과관계는 주장하지 않습니다.** 부서·채용경로를 통제한 로지스틱 회귀도 유의하지 않았고(p=0.45) 완전분리 문제로 모델 신뢰도 자체가 낮아, 상관관계·방향성까지만 유지하고 판단은 보류·모니터링 중입니다(`내도메인.md` 참고).

## 알려진 한계 (현재 미해결)

- `06_metrics/`에는 `avg_overtime`, `high_overtime_employee_rate`, `overtime_increase_rate_3m`, `vacancy_gap_days` 4개 지표 정의만 있습니다. `_INDEX.md`가 기억하는 나머지 6개(전사 퇴사율, 부서별 퇴사율, 근속기간, 평가점수, 채용경로별 지표, 부서별 초과근무)는 정의 파일이 없고, 현재 `app.py`에 계산 로직이 직접 들어가 있습니다 — 엔진 밖에서 관리되는 상태입니다.
- `retention_target_rate`(목표 잔류율 달성률)는 `calc_metrics.py`가 지원하는 4개 계산 방식(`ratio`/`mean`/`pct_threshold`/`pct_change`) 중 어디에도 맞지 않아, 의도적으로 엔진에 편입하지 않고 `app.py`에서 직접 계산합니다.
- 연차별 잔류율(Kaplan-Meier)과 우측절단 코호트 필터링도 같은 이유로 `app.py`에서 직접 계산합니다.

## 이식 안내 (다른 데이터셋/프로젝트로 옮길 때)

이 프로젝트 구조 자체는 데이터셋에 무관하게 재사용할 수 있도록 설계되어 있습니다. 옮길 때 손봐야 할 곳은 다음과 같습니다.

1. `data/`의 CSV 4종을 새 데이터로 교체하고, 컬럼명이 다르면 `데이터_조인_규칙서.md`와 `calc_metrics.py`의 `PATHS`·조인 로직을 새 컬럼명에 맞게 고칩니다.
2. `06_metrics/*.md`의 프론트매터(`table`, `value_col`, `groupby` 등)를 새 데이터의 컬럼명에 맞게 다시 씁니다. 계산 로직(`calc_metrics.py`)은 원칙적으로 고칠 필요가 없습니다.
3. `app.py`의 하드코딩된 상수(`TARGET_RETENTION_RATE`, `REASON_ORDER`, `CHANNEL_ORDER` 등)를 새 조직의 실제 값으로 교체합니다.
4. `01_questions/`~`04_insights/`의 질문·분석·인사이트는 새 프로젝트의 질문으로 다시 작성합니다 — 이 부분만큼은 데이터셋마다 새로 채워야 하는 영역입니다.
